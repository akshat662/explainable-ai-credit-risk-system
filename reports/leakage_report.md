# Leakage Audit Report

Generated by `src/features.py` (Step 1: dataset comparison) and
`src/leakage_experiment.py` (Step 2: model comparison), on development
data only. `holdout.parquet` was not read at any point in this audit.

## 1. Dataset comparison

`features_naive.parquet` aggregates all bureau/previous_application rows.
`features_filtered.parquet` restricts bureau to `DAYS_CREDIT <= 0` and
previous_application to `DAYS_DECISION <= 0` before aggregating — i.e. it
excludes any record that, on its face, originated after the current
application's decision date.

| Check | Result |
|---|---|
| Row count | 307,511 in both |
| SK_ID_CURR coverage | Identical — 0 IDs present in one but not the other |
| TARGET (default) distribution | Naive 8.0729% vs filtered 8.0729% — identical |
| Feature values | **Value-identical**, up to floating-point noise (see below) |

**Floating-point noise, not a data difference.** A raw `EXCEPT` comparison
of the two Parquet files initially showed 29,533 differing rows. Column-
by-column inspection traced every difference to `AVG`/`SUM`-based
aggregate columns (`bureau_avg_credit`, `bureau_total_credit`,
`bureau_total_debt`, `prev_avg_requested`, `prev_avg_granted`,
`prev_grant_ratio`, `debt_income_ratio`), with a maximum absolute
difference of **4.44e-16** — machine epsilon. As a control, the naive
pipeline was independently rebuilt twice with the *same* filter argument
(`time_filtered=False` both times) and diffed against itself: 26,532 rows
differed, at the same ~1e-16 magnitude. This confirms the differences come
from DuckDB's parallel hash-aggregation not guaranteeing a fixed
floating-point summation order across runs — not from the temporal
filter. At 1e-16 relative magnitude, this is far below the precision of
the underlying financial figures and has no effect on any histogram-based
model split.

## 2. Temporal filtering assumptions

| Field | Used as filter? | Finding |
|---|---|---|
| `bureau.DAYS_CREDIT` | Yes (`<= 0`) | **100% of 1,716,428 rows already satisfy this** (observed range: -2922 to 0). The filter excludes 0 rows. |
| `previous_application.DAYS_DECISION` | Yes (`<= 0`) | **100% of 1,670,214 rows already satisfy this** (observed range: -2922 to -1). The filter excludes 0 rows. |
| `bureau.DAYS_CREDIT_UPDATE` | **No — reported only** | See analysis below. Distinct from `DAYS_CREDIT`: it marks when a bureau record was last *refreshed*, not when the underlying loan *originated*. |

**DAYS_CREDIT_UPDATE analysis** (full output in
`reports/days_credit_update_analysis.json`, produced by
`analyze_days_credit_update()` in `src/features.py`):

- Range: -41,947 to **+372** days relative to the current application.
- Quantiles: p50 = -395, p90 = -13, p99 = -3, p100 = +372.
- **17 of 1,716,428 rows (0.0010%)** have `DAYS_CREDIT_UPDATE > 0` — all on
  already-`Active` loans whose origination (`DAYS_CREDIT`) is confirmed
  `<= 0`.

**Decision: not used as a filter.** A positive `DAYS_CREDIT_UPDATE` means
that record's snapshot fields (e.g. `CREDIT_DAY_OVERDUE`,
`AMT_CREDIT_SUM_DEBT`) were refreshed after the application decision date —
a real, if narrow, leakage vector distinct from the one this experiment
tests. It affects too few rows (17) to move any aggregate measurably, so
it was not filtered here; the affected rows are documented above rather
than silently assumed safe. This is a candidate for a follow-up,
finer-grained audit, not resolved by this experiment.

## 3. Performance comparison

Stratified 3-fold CV, identical `XGBClassifier` config
(`tree_method=hist, n_estimators=300, learning_rate=0.1, max_depth=6,
subsample=0.8, colsample_bytree=0.8, eval_metric=aucpr, random_state=42`),
identical CV splits (`random_state=42`), both arms row-aligned by
`SK_ID_CURR`, 246,008 development-set rows, 131 numeric/boolean features.
Full output in `reports/leakage_results.json`.

| Metric | Naive | Filtered |
|---|---|---|
| ROC-AUC (mean ± std) | 0.7638 ± 0.0012 | 0.7638 ± 0.0012 |
| PR-AUC (mean ± std) | 0.2494 ± 0.0063 | 0.2494 ± 0.0063 |

Results are identical to the reported precision. This is the expected
outcome given Section 1: the two training tables differ only at the
1e-16 floating-point level, which XGBoost's histogram binning cannot
distinguish, so the model sees effectively the same data in both arms.

## 4. Interpretation

**Conclusion: Further investigation required** — this experiment is
inconclusive by construction, not merely "clean."

The audit did not find evidence of leakage, but it also did not have the
statistical power to find any: the temporal filter it tests
(`DAYS_CREDIT <= 0`, `DAYS_DECISION <= 0`) turned out to already hold for
100% of the raw bureau/previous_application data, so "filtered" and
"naive" are the same experiment run twice. A true test of record-
origination-timing leakage would require either (a) a dataset where such
violations actually exist, or (b) directly testing a different, narrower
hypothesis — most concretely, the 17-row `DAYS_CREDIT_UPDATE > 0`
population, or the bureau snapshot-staleness question in general (are
`CREDIT_DAY_OVERDUE` / `AMT_CREDIT_SUM_DEBT` values reflecting a status
date meaningfully after the application decision, even when
`DAYS_CREDIT_UPDATE <= 0`?).

What this audit *does* rule out: bureau/previous_application records that
are literally future-dated relative to the application are not a leakage
source here, because none exist. What it does *not* rule out: leakage via
external score fields (`EXT_SOURCE_1/2/3`, unmodified by this experiment,
present in both arms identically) or via bureau field semantics not
captured by `DAYS_CREDIT`/`DAYS_DECISION` alone.
